# 10 月 3 日 HSET 索引发布诊断

## 测量范围

当前 main 为 `44761b91`。第一轮 #244 `62507324` 仅减少发布时的分配和重复查找，100 MiB Hash/Set 的四组清盘对照没有稳定提升。最新 #244 `faaaba58` 增加物理坐标合并，正在独立重新测量；旧数据不会作为新版结果。

CPU 诊断为第一轮 #244 的 HSET：500 keys × 100 MiB/key、1 KiB/field、1,280 连接。正式曲线完成后，在恢复后的同一数据集上单独运行 30 秒；12 个活动 worker 分别以 task-clock 99 Hz、DWARF 16 KiB 采样 25 秒。该诊断不进入吞吐曲线。

[全 worker 汇总](pr244-hset-perworker-summary.json) 合计 259.64 CPU 秒，约 74.06% 用户态、25.94% 内核态，没有缺失调用链。这里的百分比以记录的总 CPU 时间为分母，包含轮询、后台清理和内核处理，不能当作请求延迟比例。

## 发现与尝试

- 分配器 self CPU 合计约 7.97%；其中可辨认的物理索引分配约 2.23%，路由节点分配约 1.86%。协程边界外无法归因的部分没有硬归到请求路径。
- `FindRecord` self 约 3.33%，包括前台约 1.77%、搬迁约 1.02%、退役检查约 0.37%。`HashGroupDirectory::Find` 约 2.49%。
- 路由 `SetNode` 约 2.18%、`UpdatePhysical` 相关 self 约 1.99%；`memmove` self 约 1.49%。

物理索引之前对每次坐标变更立即复制路径和 64 项索引页。新版在不可变视图里合并少量已有内联记录的坐标更新，共享原索引；容量溢出、新身份或外部 extent 会合并并完整回写。查找和生命周期遍历返回最新坐标，旧快照保留自己的视图。只保存坐标元数据，没有缓存字段或页内容。String 保持原有位置索引。

这些采样提示可减少的 CPU 工作，但尚不能证明它解释了与 Kvrocks 的全部差距，也不能证明磁盘等待不是瓶颈。新版收益以独立、无 perf 的同机 main/PR 对照为准。

## 新版结果：100 MiB Hash / 1 KiB field

新版 `faaaba58` 的独立清盘、恢复、逐 key 前后校验均通过，全部 13 个正式测点零错误。[正式五库曲线](../../charts/hash-104857600-1024-ab.png) 中，HSET 五档连接相对 main `44761b91` 提升 14.4%～23.9%；峰值从 152,397 到 185,851 QPS（+22.0%）。这是本轮一次连接扫描，不是重复测量的统计估计。HGET 峰值从 596,054 到 578,928 QPS（−2.9%），需要在更大范围负载中检查额外元数据对读取的影响。

[新版 CPU 汇总](pr244-overlay-hset-perworker-summary.json) 使用相同的单独采样协议，总计 265.98 CPU 秒，用户态约 71.00%、内核态约 29.00%。分配器 self 合计从第一轮 7.97% 降到 6.19%，但这两个占比不是新 main 和 PR 的直接比较。代码内联会改变符号和调用栈归因，因此不能把原 `FindRecord`、`UpdatePhysical` 符号减少视作完整逻辑成本消失。带 perf 的诊断 QPS 从 113,176 到 143,060；它们不进入正式曲线。

目前 HSET 仍低于历史 Kvrocks 同负载的峰值 344,461 QPS。Kvrocks 的 WAL/cache 配置及本轮存储设备变化见报告开头，不能由 CPU 占比直接推断剩余吞吐差距的来源。
