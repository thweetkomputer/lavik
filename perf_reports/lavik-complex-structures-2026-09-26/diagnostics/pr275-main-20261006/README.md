# PR #275：rebase 到 main 后的 Stream 复测

[#275](https://github.com/eloqdata/lavik/pull/275) 已 rebase 到 main `d88a5e8f`，最终候选为 `fd2972b0`。60/60 个观测点和原始数据核验完成。**继续保留 draft，暂不建议合并**：大 Stream 全量读取提升明显，但小 Stream 全量读取的 p99 回退在三轮中全部复现。

- 100 MiB/key 全量 XRANGE：c1/c4/c16 配对 QPS 中位分别 **+325.49% / +238.95% / +130.87%**，三轮全部改善；p99 中位分别 −76.99% / −60.64% / −41.50%。
- 64 KiB/key 全量 XRANGE c80：QPS 中位 +0.02%，p99 **+39.07%**；三轮 main 为 3.727 / 3.791 / 3.743 ms，候选为 5.183 / 5.247 / 5.279 ms。旧基线上的同类回退在新 main 对照中仍然存在，不能把它解释为已经被 rebase 消除。
- 点读 QPS：大对象 −0.09%，小对象 −0.83%；小对象单轮 −4.08% / +0.57% / −0.83%，没有稳定收益。
- XADD MAXLEN：大对象 c320/c5120 中位 +2.00% / +4.17%；小对象 c2560/c5120 中位 +0.59% / −1.38%。四个条件的单轮 QPS 方向均有正有负，不能据此称为稳定写入优化。大对象 c320 p99 三轮均变差（中位 +1.14%，最差 +19.86%）。

该实现有明确的大范围读取价值，保留候选有意义；下一步应先定位并消除小范围读取尾延迟回退，再评估合并。此次仅完成 rebase、必要的测试兼容修正和复测，没有为了掩盖控制组结果而修改生产候选。

## 本轮对象与方法

- main：`d88a5e8fdcc5702272b26f9853f4baad7a146988`；候选：`fd2972b0f9ea9ccda5d231dd0d4984d9ee1b44e5`。两者在同一本机 GCC13/native/SPDK 构建缓存中分别配置、构建、冻结并验证，生产二进制均关闭测试故障注入。完整身份、依赖、构建配置和测试结果见 [版本证据](pr275-versions.json)。
- 新构建的 main 数据面二进制 SHA256 为 `e230e51346bbe9f980b401081c82e0eac0269f9a1ed29a4d24371d4ff854fd84`，与此前 `5a3903d9` 的数据面二进制相同；本轮仍保留实际构建与测试的 `d88a5e8f` 提交身份。候选 SHA256 为 `1a6af6db8f30b91892d6f10666e39c35400e071c9c3dc609248c298df668a5c7`。
- 10 个条件 × 3 轮 × 2 版本，共 60 个观测点。每点 30 秒，pipeline=1，12 workers，三轮按 main/候选、候选/main、main/候选运行。六块专用 NVMe 使用 SPDK，客户端通过 TCP；配置与旧 Stream 对照保持一致。
- 每个读配对先由 main 逐条 XADD 新建数据，再让两个版本分别重启读取同一份不变数据。大对象进程依次测 full XRANGE c1/c4/c16、点 XRANGE c2560；小对象依次测 full XRANGE c80、点 XRANGE c5120。
- 写入每个版本独立重新预置，随后大对象按 c320→c5120、小对象按 c2560→c5120 测 XADD MAXLEN。每次运行后逐 key 核验，允许 MAXLEN 近似修剪已有的最多 100 条余量。不同连接数在同一写入进程中顺序测量，并非各自重新预置。
- 核验所有原始结果与汇总一致，固定源提交和二进制 SHA、读配对共享的预置来源、所有 key 的基数、错误记录和正常退出。见 [完整核验与三轮统计](complete-summary.json)、[协议](protocol.json)、[原始观测索引](pr275-rebased-repeats.json) 和 [证据文件索引](evidence-index.json)。
- 测量期间没有并行的本机构建、原生测试或 perf。Hash/Set 的压测与 perf 全部结束后才开始本轮构建；原生验证通过后才开始 Stream 吞吐测试。测试和基准各使用独立挂载命名空间，将工作盘上的临时目录映射到进程的 `/tmp`，宿主 `/tmp` 不变。

## 验证与 rebase 修正

原 PR 的六个补丁无冲突 rebase 到 `d88a5e8f`，`range-diff` 全部一致。第一次 rebased head `eccea5c7` 的 [CI](https://github.com/eloqdata/lavik/actions/runs/37452841525) 发现两处测试 mock 与 main 新接口不匹配，amd64/arm64 均出现：Data-control mock 未接收 `timeout` 关键字，以及重试测试未模拟新增的成员稳定性探测，误走真实 CLI 路径而触发 `CTL` 未定义。

`fd2972b0` 只修正这两处 Python mock，并加强对应调用检查；生产代码和超时设置未改。10 项本地 Python 回归以及 Ruff/格式检查通过。失败日志和修正验证保留在本目录，详见 [失败诊断](fixture-failure.json)。第一次 rebased CI 的有序结构 E2E 在两个架构均通过；不能把那两项 fixture 失败误称为 Stream 存储失败。

两个固定生产版本各通过 128 项单元测试和 74 项有序结构 E2E；main/candidate 分别跳过 34/35 项故障注入用例。此外，各自再独立重复三轮 `LargeRdbRoundTripKeepsMessagesAndDeletedPendingBounded` 和 `ReclaimsGraphAndRecovers/ListIndirect`，全部通过，超时未加长。故障注入覆盖由独立的 CI 配置提供，生产构建的跳过项不算成功执行。

此前旧版本曾出现的 Stream XREADGROUP 接收超时和 arm64 ListIndirect RESTORE 超时，本轮未复现，根因仍未得到解释。后来的通过不能抹掉原始失败，也不能把它们归因于另一次已知的 `/tmp` 空间问题。旧证据和性能表见 [历史 Stream 报告](../stream-reply-20261004/README.md)，不与本轮结果合并统计。

## 解释范围

本轮是 rebase 后的功能与吞吐复测，没有重新采集 #275 的 perf；旧 perf 只作为具名历史二进制的诊断证据。不能将旧 CPU 占比直接标为当前 head 的热点。

三轮配对不等于统计置信区间。大对象全量读的完成请求数较少，QPS 输出保留两位小数，c1 多轮相同的比值受量化影响；尾延迟也不能视为精确的总体 p99。只比较这些固定负载，不证明所有 Stream 命令都提速。其他三个系统未重测，本报告不建立与它们的性能或持久性等价结论。
